## `prefab_store.py`

Read this file as the in-memory prefab inventory that setup import feeds and later runtime systems consume. The important point is that `PrefabStore` is not just a dictionary. It also maintains rotation queues so plane prefab selection can be balanced over time.

## Store Structure And Indexes

The store maintains several views over the same imported prefab data:

- `prefabs` as the raw imported list
- `prefab_by_name` for direct lookups
- grouped queues for plane selection by type, range, or both

That structure is what lets setup import stay simple while still supporting smarter runtime selection later.

<TransportCodeBlock title="prefab_store.py">
```python
class PrefabStore:
    def __init__(self):
        self.prefabs: list[dict] = []
        self.prefab_by_name: dict[str, dict] = {}

        self._plane_names: set[str] = set()

        self._planes_by_type: dict[str, deque[str]] = defaultdict(deque)
        self._planes_by_range: dict[str, deque[str]] = defaultdict(deque)
```

## Add One Prefab: Validation And Classification

`add_prefab(...)` is the core mutation path. It always records the raw prefab first, then conditionally adds richer plane-specific indexes if the prefab qualifies.

The two main dependencies are the mapping helpers:

- `type_for_airplane_model(...)`
- `range_for_airplane_model(...)`

Those helpers convert a prefab name into the selection categories used later.

<TransportCodeBlock title="prefab_store.py">
```python
def add_prefab(self, prefab: dict) -> None:
    """Store the prefab"""

    self.prefabs.append(prefab)

    name = prefab.get("name")
    if not isinstance(name, str) or not name:
        return
    self.prefab_by_name[name] = prefab

    if str(prefab.get("type", "")).lower() != "plane":
        return

    if name in self._plane_names:
        return

    try:
        airplane_type = type_for_airplane_model(name)
        airplane_range = range_for_airplane_model(name)
    except ValueError:
        return
```

## Batch Import Entry Point

This is the method `setup_bus.py` actually calls during prefab commit. Its job is intentionally small: validate each item is a dict and then reuse `add_prefab(...)`.

That keeps all classification logic centralized in one place.

<TransportCodeBlock title="prefab_store.py">
```python
def add_prefabs(self, payload: list[dict]) -> None:
    """Add multiple prefabs from the batch payload from Unity"""

    for prefab in payload:
        if isinstance(prefab, dict):
            self.add_prefab(prefab)
```

## Selection Logic: Exact Match To Fallback

`pick_plane_prefab(...)` is where the indexed queues start to matter. The matching order is:

1. exact `flight_type` plus `required_range`
2. `flight_type` only
3. `required_range` only
4. any available typed-range queue as a last fallback

When a queue is used, it rotates left so the next request gets a different prefab first.

<TransportCodeBlock title="prefab_store.py">
```python
def pick_plane_prefab(self, flight_type: str | None, required_range: str | None) -> str | None:
    """Chose the best matching plane for the flight required"""

    q = None
    if flight_type and required_range:
        q = self._planes_by_type_range.get((flight_type, required_range))
    if not q and flight_type:
        q = self._planes_by_type.get(flight_type)
    if not q and required_range:
        q = self._planes_by_range.get(required_range)

    if q:
        name = q[0]
        q.rotate(-1)
        return name
```
