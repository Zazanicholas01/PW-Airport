# End-to-end workflows

This topic consolidates the “End-to-End Workflows” sections from `../../../README.md` and the transport/handler/scheduler guides.

## 1) Startup + setup handshake (Unity -> Python)

1. Unity connects to `ws://localhost:8765` (see `../../../Unity_Scripts/UnityWSClient.cs`).
2. Unity sends spline batch (`setup-init`, `send-splines`, spline payloads, `finish-send-splines`).
3. Unity sends prefab batch (`send-prefabs`, prefab list, `finish-send-prefabs`).
4. Backend setup handler:
   - stores prefabs in `../../domain/prefab_store.py`
   - extracts stand/spawn positions from splines
   - builds full landing/departure paths via `../../init_graph.py`
   - persists paths (`Path`/`Percorso`) into DB
   - marks setup complete

## 2) Flight lifecycle scheduling (authoritative in Python)

The flight scheduler loop in `../../transport/ws_server.py`:

- generates an initial randomized dataset (`../../services/flight_generator.py`)
- continuously queries a sliding window (`../../db/db_functions.py`)
- applies stage guards/decisions (`../../schedulers/flight_scheduler.py`)
- emits Unity commands (`start_path`, `spawn_plane`)

## 3) Runtime event handling (Unity -> Python)

Unity emits runtime events such as:

- `path_completed`
- `plane_left_stand`

Backend processes them in `../../handlers/runtime_bus.py`, updating airplane/flight/stand status and managing disembark timers in *simulation time*.
