## Setup Import Contract

<DocsSteps items={setupFlow} variant="timeline" />

### Unity Control Events

These are the setup-phase control events handled by `SetupBusHandler`:

- `setup-init`
- `send-splines`
- `finish-send-splines`
- `send-prefabs`
- `finish-send-prefabs`

### Example Spline Payload

```json
{
  "type": "event",
  "event": "spline",
  "spline": {
    "name": "Spline_O1",
    "firstKnotPos": { "x": 0, "y": 0, "z": 0 }
  }
}
```

### Example Prefab Batch

```json
{
  "prefabs": [
    { "name": "a320" },
    { "name": "b737" }
  ]
}
```

## Runtime Event Contract

After setup completes, runtime payloads are expected to be `type="event"` objects. The currently relevant runtime event names are:

- `path_completed`
- `plane_left_stand`

Both runtime handlers expect an `airplane_id`, and `path_completed` is interpreted by looking up the current route destination in the database.

### Example Runtime Event

```json
{
  "type": "event",
  "event": "path_completed",
  "airplane_id": "plane-123"
}
```

## Python To Unity Command Contract

These are the command shapes built in `src/transport/command_builders.py`.

### Welcome

```json
{
  "command": "welcome",
  "type": "welcome",
  "message": "Connected to Python server"
}
```

### Clock Sync

```json
{
  "command": "clock_sync",
  "sync_id": 42,
  "sim_unix_ms": 1774838400000,
  "time_scale": 1.0
}
```

### Spawn Plane

```json
{
  "command": "spawn_plane",
  "prefab": "a320",
  "stand_id": "P1",
  "position": { "x": 0, "y": 0, "z": 0 },
  "airplane_id": "plane-123",
  "spawn_context": "landing"
}
```

### Start Path

```json
{
  "command": "start_path",
  "airplane_id": "plane-123",
  "route_id": 17,
  "speed": 0.2,
  "segments": []
}
```

### Clock Control Commands From Unity

Clock control is the main command-shaped payload Python consumes directly in transport before handler routing:

- `set_time_scale` with `time_scale` and optional `request_id`
- `set_sim_time` with `sim_unix_ms`

## Dashboard Feed Contract

The web dashboard consumes two different payload families.

### JSONL Event Log Records

`src/utils/event_log.py` writes one JSON object per line to `data/logs/events.jsonl`. The current important event shapes are:

- `{"type":"clock","sim_unix_ms":...,"time_scale":...,"sync_id":...}`
- `{"type":"backend_event","event":"departure_assigned",...}`
- `{"type":"log","level":"INFO","subsystem":"...",...}` when present in the log stream

### Browser WebSocket Payloads

The browser-facing FastAPI WebSockets use a small `kind` envelope:

- `/ws/events`: `{"kind":"snapshot","events":[...]}` and `{"kind":"append","events":[...]}`
- `/ws/clock`: `{"kind":"sync","clock":{...}}`
- `/ws/window-flights`: `{"kind":"snapshot","window":{...}}`
- `/ws/planes-ground`: `{"kind":"snapshot","planes":{...}}`

## Canonical Vocabulary

These shared values come from `src/domain/status_constants.py` and should be treated as the contract vocabulary across transport, DB helpers, handlers, schedulers, and dashboard rendering.

## Contract Rules

- Use exact string values from `status_constants.py` for statuses, event names, and bus commands.
- Treat `clock_sync` and JSONL `type="clock"` records as related but different contracts: one is Unity-facing over WebSocket, the other is dashboard-facing via the event log.
- Treat dashboard snapshots as display-oriented payloads, not raw ORM objects.
- Keep `type="event"` runtime payloads small and explicit; runtime meaning is resolved server-side from DB state.
- Keep setup control events separate from runtime events. The setup handler ignores late setup payloads once the setup phase is complete.
